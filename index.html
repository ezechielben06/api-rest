Construire une API REST pas à pas

Tu vas écrire une API de gestion de produits pour un magasin, sans framework. Chaque fichier est expliqué ligne par ligne. À la fin, tu testes tout dans un simulateur qui montre quelle couche traite chaque requête.

Comprendre

Ce que tu vas construire

Une API qui permet de lister, ajouter, modifier et supprimer les produits d'un magasin. Pas de ventes, pas de catégories, pas d'alertes pour l'instant. On commence simple.

Méthode URL Action Succès Échec
GET /produits Lister tous les produits 200 aucun cas prévu
GET /produits/{id} Lire un produit 200 404
POST /produits Ajouter un produit 201 400
PUT /produits/{id} Modifier un produit 200 400
DELETE /produits/{id} Supprimer un produit 200 404

Ce qu'il faut savoir avant de commencer

  • Écrire un peu de PHP : variables, fonctions, tableaux.
  • Savoir ce qu'est une base de données MySQL.
  • Avoir installé XAMPP ou WAMP, qui fournissent MySQL.
  • Savoir utiliser un terminal simple.

Si tu ne sais pas tout ça, ce n'est pas grave. Chaque ligne de code du cours est commentée pour te guider.

Comprendre

Les bases de REST

Une API est un contrat entre deux programmes. Le client (navigateur, application mobile, script) envoie une requête HTTP. Le serveur répond. Le client ne sait rien de PHP ni de MySQL : il connaît seulement l'URL et le format des données.

REST est une manière d'organiser ce contrat. Les choses que l'on manipule s'appellent des ressources (ici, les produits) et chacune a une URL. Les actions sont exprimées par le verbe HTTP. Les données voyagent en JSON. Le serveur ne garde aucun souvenir entre deux requêtes : chaque requête contient tout ce qu'il faut pour être traitée.

Anatomie d'une URL

http://protocole
localhosthôte
:8000port
/produitsressource
/3identifiant

Le protocole dit comment parler, l'hôte et le port désignent la machine et le programme qui écoute, la ressource dit quelle collection on vise, l'identifiant désigne un élément précis. Sans identifiant, on parle de toute la collection.

Anatomie d'une requête et d'une réponse

POST /produits HTTP/1.1
Host: localhost:8000
Content-Type: application/json

{"nom":"Lait","prix":800,"stock":15}
HTTP/1.1 201 Created
Content-Type: application/json

{"id":"3","message":"Produit créé"}
Première ligne : méthode, chemin, version, ou code de statut Nom d'un en-tête Valeur d'un en-tête Corps du message (après une ligne vide)

Les en-têtes sont des informations sur le message : le type de contenu, la taille, la langue. La ligne vide sépare les en-têtes du corps. Une requête GET n'a en général pas de corps.

Les verbes HTTP et le CRUD

Opération Verbe SQL Méthode du Controller
Créer POST INSERT store()
Lire la liste GET SELECT index()
Lire un élément GET SELECT … WHERE id show($id)
Modifier PUT UPDATE update($id)
Supprimer DELETE DELETE destroy($id)

PUT remplace la ressource en entier, c'est pourquoi on renvoie nom, prix et stock à chaque modification. Il existe aussi PATCH pour modifier une partie seulement, mais il n'est pas utilisé dans ce TP.

Les codes de statut utilisés

Code Nom Signification Où dans le TP
200 OK La requête a réussi. index, show, update, destroy
201 Created Une ressource vient d'être créée. store
400 Bad Request Le client a envoyé des données invalides. store, update
404 Not Found La ressource ou la route n'existe pas. show, destroy, route inconnue
500 Internal Server Error Bug ou panne côté serveur. erreur PHP non attrapée

Retiens la règle simple : 2xx signifie que tout va bien, 4xx signifie que la faute vient du client, 5xx signifie que la faute vient du serveur.

JSON en trente secondes

  • Un objet est entouré d'accolades et contient des paires "clé": valeur.
  • Les clés et les textes utilisent des guillemets doubles, jamais des apostrophes.
  • Les valeurs possibles sont : texte, nombre, true/false, null, tableau [ ] et objet { }.
  • Pas de virgule après le dernier élément.
  • En PHP, un tableau associatif devient un objet JSON avec json_encode(), et json_decode($texte, true) fait l'inverse.

Une architecture en couches

Le TP sépare le code en quatre fichiers, plus le point d'entrée. Chaque couche a un seul métier et ne fait pas celui des autres.

Routeurpublic/index.php

Rôle. Lire la méthode HTTP et l'URL, puis choisir la bonne méthode du Controller.

Jamais. De logique métier ni de SQL.

appelle
Controllersrc/ProduitController.php

Rôle. Lire la requête, appeler le Service, renvoyer du JSON avec le bon code de statut.

Jamais. De règles de validation ni de SQL.

appelle
Servicesrc/ProduitService.php

Rôle. Appliquer les règles du magasin : nom obligatoire, prix positif, stock non négatif.

Jamais. De codes HTTP, de JSON ni de SQL.

appelle
Repositorysrc/ProduitRepository.php

Rôle. Exécuter les requêtes SQL et renvoyer les résultats.

Jamais. De règles métier.

utilise
Basesrc/Database.php

Rôle. Ouvrir la connexion à MySQL, où les produits sont stockés.

Jamais. De requêtes sur les produits.

Les fichiers du projet

magasin/
├── public/
│   └── index.php                  ← routeur, toutes les requêtes passent ici
├── src/
│   ├── Database.php               ← connexion à MySQL
│   ├── ProduitRepository.php      ← parle à la base de données
│   ├── ProduitService.php         ← vérifie les règles
│   └── ProduitController.php      ← reçoit les requêtes HTTP
└── sql/
    └── schema.sql                 ← script de création de la base

Seulement quatre fichiers dans src, pour que tu voies clairement le rôle de chaque couche sans te perdre.

Vocabulaire

On parle souvent de « MVC » pour ce découpage. Plus précisément, c'est une architecture en couches (Controller, Service, Repository). Dans une API, la « vue » se réduit à la réponse JSON. Le principe reste le même : un fichier, une responsabilité.

Le voyage d'une requête POST /produits

  1. Client

    Envoie POST /produits avec le JSON {"nom":"Lait","prix":800,"stock":15}.

  2. Routeur

    index.php lit la méthode et le chemin. Il ne reste aucun morceau après /produits, donc la condition « POST et zéro morceau » est vraie.

  3. Controller

    store() est appelée. Elle lit le corps de la requête avec php://input et le décode avec json_decode.

  4. Controller

    Elle passe le tableau au Service avec $this->service->create($data).

  5. Service

    valider($data) contrôle le nom, le prix et le stock. Si une règle échoue, une exception part et rien ne descend plus bas.

  6. Service

    Les données sont valides : il appelle $this->repo->create($nom, $prix, $stock).

  7. Repository

    Prépare l'INSERT, l'exécute avec les trois valeurs, puis lit le nouvel identifiant avec lastInsertId().

  8. Controller

    L'identifiant remonte jusqu'ici. repondre() envoie 201 et le JSON {"id":"3","message":"Produit créé"}.

Si l'étape 5 échoue, les étapes 6 et 7 n'ont jamais lieu. Le Controller attrape l'exception et répond 400.

Préparer le poste de travail

Quatre vérifications avant d'écrire du code.

  1. Démarre MySQL depuis le panneau de contrôle de XAMPP ou WAMP. Démarre aussi Apache si tu veux utiliser phpMyAdmin. L'API elle-même tournera sur le serveur intégré de PHP, donc Apache et ton API n'entrent pas en conflit.
  2. Vérifie que PHP répond dans un terminal avec la commande ci-dessous. Sous Windows, si le terminal ne la connaît pas, ajoute le dossier php de XAMPP (par exemple C:\xampp\php) à la variable d'environnement PATH, puis rouvre le terminal.
  3. Crée les dossiers du projet, avec les commandes ci-dessous ou à la main dans l'explorateur de fichiers.
  4. Prépare un éditeur de code, par exemple VS Code, et ouvre le dossier magasin.

La première commande affiche la version de PHP installée. La seconde crée l'arborescence (sous Windows PowerShell, écris mkdir magasin, magasin\public, magasin\src, magasin\sql).

Base Étape 2 sur 7

Le fichier de connexion

Ce fichier ouvre une connexion à MySQL et la renvoie. Tous les autres fichiers qui parlent à la base passent par lui.

Tester seul

Crée un fichier temporaire test.php à la racine de magasin, lance-le avec php test.php, puis supprime-le. Si tu vois « Connexion réussie », la base répond.

Repository Étape 3 sur 7

La couche Repository

Il ne fait que parler à la base de données. Aucune règle métier ici : il exécute les requêtes SQL et rend les résultats.

À retenir

Chaque requête qui reçoit une valeur de l'extérieur utilise prepare() puis execute(). Les valeurs ne sont jamais collées dans le texte SQL. C'est ce qui bloque les injections SQL.

Piège classique

Un UPDATE ou un DELETE sans WHERE touche toutes les lignes de la table. Relis toujours cette clause avant de lancer.

Service Étape 4 sur 7

La couche Service

Elle vérifie que les données respectent les règles du magasin avant de les envoyer à la base. Si demain tu changes de base de données, seul le Repository change et le Service reste identique.

Les règles métier du TP

Champ Règle Message de l'exception
nom Obligatoire, non vide Le nom est obligatoire
prix Présent et strictement supérieur à 0 Le prix doit être supérieur à 0
stock Présent et supérieur ou égal à 0 Le stock ne peut pas être négatif
Exceptions

Le Service ne sait pas ce qu'est HTTP. Quand quelque chose ne va pas, il lève une exception avec throw. L'exécution s'arrête net et remonte jusqu'au catch du Controller, qui choisit le code de statut.

Controller Étape 5 sur 7

La couche Controller

Elle reçoit les requêtes HTTP, appelle le Service et renvoie une réponse JSON. Elle ne contient aucune règle métier.

Du métier au HTTP

Méthode Si tout va bien Si le Service lève une exception
index() 200 + liste aucune attrapée
show($id) 200 + produit 404
store() 201 + id 400
update($id) 200 400
destroy($id) 200 404
Observe bien

Dans update(), un produit inexistant donne 400 alors que dans destroy() il donne 404. C'est une petite incohérence du TP, que tu peux constater dans le simulateur et corriger dans la section « Aller plus loin ».

Routeur Étape 6 sur 7

Le point d'entrée

Toutes les requêtes arrivent dans public/index.php. Il lit la méthode et l'URL, puis décide quelle méthode du Controller appeler.

Comment l'URL devient une route

Requête Chemin $morceaux Action appelée
GET /produits [] index()
GET /produits/3 ['3'] show('3')
POST /produits [] store()
PUT /produits/3 ['3'] update('3')
DELETE /produits/3 ['3'] destroy('3')
GET /produits/3/avis ['3','avis'] aucune : 404 « Route non trouvée »
Volontairement simple

Ce routeur ne gère que /produits. Quand tu ajouteras les catégories, tu ajouteras des conditions.

Client Étape 7 sur 7

Lancer et tester

Dans le terminal, à la racine du dossier magasin, démarre le serveur. Puis envoie des requêtes avec ton navigateur ou avec curl.

Pour la liste des produits, ouvre simplement http://localhost:8000/produits dans ton navigateur. Pour les autres opérations, utilise curl : le navigateur ne sait envoyer que des GET depuis la barre d'adresse.

Voir le code de statut

Ajoute l'option -i à curl pour afficher la ligne de statut et les en-têtes de la réponse, par exemple curl -i http://localhost:8000/produits/999.

Windows

Dans le terminal classique de Windows (cmd), le caractère \ ne continue pas une ligne et les apostrophes ne protègent pas le JSON. Écris la commande sur une seule ligne et double les guillemets du JSON : -d "{\"nom\":\"Lait\",\"prix\":800,\"stock\":15}". Dans PowerShell, écris curl.exe et non curl, qui est un alias d'une autre commande. Si les guillemets te bloquent, utilise le simulateur plus bas ou un outil comme Postman.

Les réponses attendues

Requête Statut Corps
GET /produits 200 [{"id":1,"nom":"Savon","prix":"500.00","stock":20}, …]
POST /produits 201 {"id":"3","message":"Produit cr\u00e9\u00e9"}
PUT /produits/1 200 {"message":"Produit modifi\u00e9"}
DELETE /produits/1 200 {"message":"Produit supprim\u00e9"}
GET /produits/999 404 {"erreur":"Produit introuvable"}
Deux surprises normales

Le prix arrive sous forme de texte ("500.00") parce que PDO renvoie les colonnes DECIMAL en chaînes, afin de ne pas perdre de précision. Les accents sortent sous la forme \u00e9 parce que json_encode les échappe par défaut. Un client JSON les décode sans rien faire. Le "id":"3" d'une création est lui aussi un texte, car lastInsertId() renvoie toujours une chaîne.

    Consommer l'API avec JavaScript
    
            
    
              Une API prend tout son sens quand un site s'en sert. Voici une
              petite page qui affiche les produits, en ajoute et en supprime,
              avec fetch. Enregistre les deux fichiers dans le
              dossier public.
            
    
          
    
          
    
            Comme php -S sert les fichiers qui existent,
            public/app.html s'ouvre sur
            http://localhost:8000/app.html. La page et l'API ont
            alors la même origine (même hôte et même port), donc le navigateur
            ne bloque rien.
          
    
          
    
          
    
          
    
            Pourquoi pas innerHTML
            
    
              Le nom d'un produit vient d'un utilisateur. Si tu l'insères avec
              innerHTML, un nom contenant du HTML s'exécuterait
              dans la page (faille XSS). Le code ci-dessus crée les éléments un
              par un et écrit le texte avec textContent, qui
              n'interprète jamais le HTML.
            
    
          
    
          
    
            Et si la page est ailleurs ?
            
    
              Une page ouverte depuis un autre port (par exemple Live Server sur
              le port 5500) appelle une autre origine. Le navigateur refuse
              alors la réponse sauf si l'API envoie les en-têtes CORS. Le code
              se trouve dans la section « Aller plus loin ».

    Terminer
    
            
    Soutenance et travail en binôme
    
            
    
              Même si le TP est simple, le jury peut te demander de justifier
              tes choix. Voici les questions probables, avec des réponses à
              reformuler avec tes mots.
            
    
          
    
          
    
            
    
              Pourquoi quatre fichiers au lieu d'un seul ?
              
    
                
    
                  Pour séparer les responsabilités : le Controller gère le HTTP,
                  le Service les règles, le Repository la base. Si on change
                  MySQL pour PostgreSQL, seul le Repository (et la connexion)
                  change. Le Service et le Controller restent identiques.
                
    
              
    
            
    
            
    
              
                Pourquoi prepare() et execute() au lieu de concaténer ?
              
              
    
                
    
                  Pour éviter les injections SQL. Avec une concaténation, ce que
                  l'utilisateur envoie devient du code SQL. Avec une requête
                  préparée, les valeurs voyagent séparément et ne sont jamais
                  interprétées comme du SQL.
                
    
                
                
              
    
            
    
            
    
              
                Pourquoi le Controller ne contient-il pas les règles de
                validation ?
              
              
    
                
    
                  Parce que ces règles peuvent être appelées depuis un autre
                  endroit : une commande, un test, une autre API. Elles ne
                  doivent pas dépendre du HTTP.
                
    
              
    
            
    
            
    
              Pourquoi 201 pour un POST et pas 200 ?
              
    
                
    
                  200 dit seulement que ça a marché. 201 dit en plus qu'une
                  nouvelle ressource a été créée. C'est plus précis pour le
                  client, qui peut alors utiliser l'identifiant renvoyé.
                
    
              
    
            
    
            
    
              Quelle différence entre 400 et 404 ?
              
    
                
    
                  400 signifie que la requête est mal formée ou que les données
                  sont invalides. 404 signifie que la ressource ou la route
                  demandée n'existe pas. Dans les deux cas, la faute vient du
                  client.
                
    
              
    
            
    
            
    
              Que se passe-t-il si MySQL est arrêté ?
              
    
                
    
                  La connexion échoue dans Database::connect(), qui
                  exécute die() avec un message en texte brut. Le
                  client ne reçoit donc pas du JSON propre. Améliorer cela fait
                  partie des pistes de la dernière section.
                
    
              
    
            
    
            
    
              
                Pourquoi le Service lève-t-il des exceptions au lieu de renvoyer
                un code HTTP ?
              
              
    
                
    
                  Parce que le Service ne doit pas connaître HTTP. Une exception
                  dit « quelque chose ne va pas » sans imposer la manière de le
                  dire. Le Controller traduit en 400 ou 404, une commande en
                  ligne de commande l'afficherait autrement.

    Terminer
    
            
    Aller plus loin
    
            
    
              Quand le CRUD des produits fonctionne, voici des améliorations,
              des corrections des petits défauts du TP et la suite du projet.
            
    
          
    

          
    1. Renvoyer 404 quand un produit n'existe pas dans update
    
          
    
            Crée une exception dédiée. Le Service la lève quand le produit
            manque, le Controller l'attrape avant l'exception générale.
          
    
          
          
          

          
    2. Vérifier le type des valeurs
    
          
    
            Le Service teste que le prix est présent et positif, mais pas que
            c'est un nombre. Ajoute is_numeric dans
            valider().
          
    
          

          
    3. Refuser les chemins qui ne commencent pas par /produits
    
          
    
            Avec le routeur actuel, GET /abc appelle
            show('abc') et répond « Produit introuvable » au lieu
            de « Route non trouvée ». Teste le début du chemin avant le routage.
          
    
          

          
    4. Autoriser une page située sur une autre origine (CORS)
    
          
    
            Ajoute ces lignes tout en haut de index.php, après
            $methode. Le navigateur envoie d'abord une requête
            préliminaire OPTIONS pour demander la permission avant
            un PUT, un DELETE ou un JSON. Le serveur y répond par
            204 sans corps.
          
    
          
          
    
            L'étoile autorise toutes les origines, c'est pratique en
            développement. En production, écris l'adresse exacte de ton site.
          
    

          
    5. Le module Catégories
    
          
    
            Copie exactement le même modèle : Repository, Service, Controller,
            puis des conditions dans le routeur. Commence par réfléchir à la
            table et à son lien avec les produits.
          
    
          
    
            Voir une proposition de schéma SQL
            
    
              
              
    
                La clé étrangère empêche d'associer un produit à une catégorie
                qui n'existe pas.
              
    
            
    
          
    

          
    6. Les alertes de stock
    
          
    
            C'est une requête SQL de plus dans le Repository, avec le même
            chemin Service puis Controller qu'une lecture.
          
    
          

          
    7. Le module Ventes
    
          
    
            Plus complexe. Une vente doit réduire le stock et enregistrer la
            vente en même temps, ou ne rien faire du tout. C'est le rôle d'une
            transaction : beginTransaction(), puis
            commit() si tout réussit ou rollBack() en
            cas d'erreur. À faire après les catégories et les alertes.
          
    
        
    

        
    
          
    
            Cours construit à partir du TP débutant « API magasin en PHP natif
            ». Le code des fichiers PHP est celui du TP, sans modification.
